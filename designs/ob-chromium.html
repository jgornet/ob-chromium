Summary

ob-chromium is an Emacs package that adds the chromium language to org-babel. A chromium source block holds HTML. The block can name CSS source blocks or CSS files in a :css header argument. When the user executes the block, the package assembles one HTML document from the body and the CSS, writes the document to a temporary file, starts headless Chromium on that file with --screenshot, and inserts a file: link to the PNG as the block’s result. The PNG shows inline in the org buffer and exports with the document.

The package is one Elisp file with no dependency outside Emacs and org. It needs a Chromium family browser on the machine. It runs Chromium once per block with call-process and a fresh profile directory, so a running browser does not interfere (open questions 2 and 8).

The open questions that shape the design most are the language name (open question 1), how Emacs drives Chromium (open question 2), where the CSS comes from (open question 3), and whether the image follows the viewport or the content height (open question 6).

Background

What exists today

ob-mermaid (https://github.com/arnm/ob-mermaid) is the reference for this design. It is one file, ob-mermaid.el. It defines org-babel-default-header-args:mermaid as :results file and :exports results, reads each header argument from params, builds one shell command string for mmdc, and runs it with org-babel-eval with the block body on standard input. It requires :file and returns nil. Org inserts the link to :file because :results file is set and :file is present. Its repository also carries test-example.org, test-init.el, a dev-test.sh script with check, syntax, batch and interactive commands, and mise.toml for the toolchain.

ob-html-chrome (https://github.com/nikclayton/ob-html-chrome) is the closest prior art. It defines the html-chrome language, writes the body to a temporary file beside the org file, runs chrome --headless --disable-gpu --screenshot=<file> through org-babel-eval, and returns the file name. It takes the output name from :file, then from #+NAME, then from the heading text. It passes extra flags verbatim through :flags. It depends on the f and s libraries, requires the user to set the Chrome path by hand, has no CSS support beyond what the body contains, and has not changed since 2018.

Org itself provides the parts a language needs:

  • org-babel-generate-file-param derives :file from #+NAME and :file-ext and prefixes :output-dir.
  • org-babel-execute-src-block sets the result to :file when :results contains file, whatever the execute function returns.
  • org-babel-find-named-block and org-babel-get-src-block-info give the body of a named block in the buffer.
  • org-babel-eval-error-notify shows standard error in *Org-Babel Error Output*.
  • org-src-lang-modes maps a language name to the major mode used in org-edit-special.

Headless Chromium provides the rendering. Since Chrome 112 the --headless flag runs the full browser without a window. Since Chrome 132 the old headless mode is a separate binary, chrome-headless-shell. Both take --screenshot=<path>, --print-to-pdf=<path>, --window-size=W,H, --dump-dom, --virtual-time-budget=<ms>, --timeout=<ms>, --default-background-color=RRGGBBAA, --hide-scrollbars, --force-device-scale-factor=N and --user-data-dir=<dir>. The --screenshot flag captures the window, not the full page. There is no command line flag for a full page screenshot.

Why the design changes

There is no maintained org-babel language that renders HTML and CSS to an image. ob-html-chrome is unmaintained, needs two libraries, and cannot take CSS from another block. Users who write HTML and CSS in org for documentation, slides or design notes need an image of the rendered result in the same document. The package gives that with the conventions of ob-mermaid, so a user of one package knows how the other works.

Architecture

Components

The package has one process boundary: Emacs starts Chromium with call-process and waits for it to exit (open question 2). Emacs and Chromium share only the filesystem.

Executing a block, end to end

The measurement pass runs only when :fit is content (open question 6). In the default viewport mode Chromium runs once.

Types and interfaces

Green is new, grey is org code the package calls and does not change. Nothing is changed, because the package is new. The three groups are sections of one file, not separate files (open question 12).

Schema and messages

The package has no database and no network messages. Its two interfaces are the header arguments it reads and the command line it writes.

States

No component changes state. Each execution is one pass from block to file. This section has nothing more to say.

Goals and non-goals

Goals

  • Execute a chromium source block and insert a file: link to a PNG that shows the rendered HTML and CSS.
  • Take CSS from named css source blocks in the same buffer and from CSS files, through one header argument.
  • Work with any Chromium family browser found on exec-path or at the usual install paths, with no configuration when one is installed.
  • Depend on nothing outside Emacs 27.1 and org 9.4.
  • Follow the conventions of ob-mermaid: :results file, :exports results, :cmdline pass-through, one defcustom for the executable path.
  • Report a Chromium failure with Chromium’s standard error, and stay silent on success.
  • Carry the test harness of ob-mermaid: a test org file, a test init file, a script with check, syntax, batch and interactive commands, and CI.

Non-goals

  • Screenshots of remote URLs. The body of the block is the content.
  • Element capture by CSS selector in the first version (open question 10).
  • Asynchronous execution. Chromium runs in about 1 s and the user waits.
  • Sessions. org-babel-prep-session:chromium signals an error.
  • :var substitution into the HTML. Noweb references work because org expands them before the execute function runs.
  • Remote files over Tramp.
  • Browsers outside the Chromium family.
  • A live preview or a persistent browser process.

Design

Language name and editing mode

The language is chromium. A block starts with #+begin_src chromium (open question 1). On load the package adds ("chromium" . mhtml) to org-src-lang-modes, so org-edit-special opens the body in mhtml-mode with HTML, CSS and JavaScript highlighting. The language is not html, because an org-babel-execute:html function would make C-c C-c on every existing html block try to render it, and every such block would then need :file.

Default header arguments

(defvar org-babel-default-header-args:chromium
  '((:results . "file") (:exports . "results") (:file-ext . "png")))

:results file makes org use :file as the result (What exists today). :file-ext png lets a named block omit :file: org derives <name>.png in :output-dir (open question 5). The package declares every header argument it reads in org-babel-header-args:chromium, so completion and org-lint know them.

Where the CSS comes from

The :css header argument is a list of items separated by spaces (open question 3). The package resolves each item in order:

  1. When a source block in the current buffer has that #+NAME, the item is that block’s body. The block’s language is not checked, so a scss block that the user has compiled by other means still works as long as its body is CSS.
  2. Otherwise, when a file with that name exists relative to default-directory, the item is the file’s contents.
  3. Otherwise the package signals user-error with the item name and stops before Chromium starts.

The package joins the resolved bodies with a newline, in the order given, and puts them in one <style> element. It reads the file or block, it does not link to it, so the temporary document has no dependency on where it is written. The :css header argument can be set once for a subtree or a file with #+PROPERTY: header-args:chromium :css theme. A block with a <style> element in its body keeps it. Noweb references, <<theme>> in the body with :noweb yes, also work and need nothing from the package.

Assembling the document

ob-chromium--full-document-p returns true when the body, after leading whitespace, starts with <!doctype or <html in any letter case (open question 4).

When the body is a fragment, the package fills ob-chromium-template with format-spec: 

(defcustom ob-chromium-template
  "<!DOCTYPE html>
<html>
<head>
<meta charset=\"utf-8\">
<base href=\"%u\">
<style>
%c
</style>
</head>
<body>
%b
</body>
</html>"
  "Document the package wraps around a fragment.
%u is the file URL of the org file's directory, %c the CSS, %b the body.")

When the body is a full document, the package inserts <base href> and the <style> element before the first </head>. When there is no </head>, it inserts them after the first <html ...> tag. The body is otherwise unchanged.

<base href> points at default-directory of the org buffer, so an <img src“figure.png”>= in the body resolves beside the org file, wherever the temporary document is written (open question 7).

org-babel-expand-body:chromium returns the assembled document. The user sees it with C-c C-v v, org-babel-expand-src-block. That is the first debugging step when a render is wrong.

Where the temporary files go

The package writes the document to ob-chromium-<hash>.html in ob-chromium-temporary-directory when that is set, and otherwise in org’s org-babel-temporary-directory (open question 7). The hash is the first 8 characters of the SHA-1 of the assembled document. The package creates a profile directory ob-chromium-profile-<hash> in the same place and passes it as --user-data-dir (open question 8). Both are deleted after Chromium exits, on success and on failure. With :keep-html yes the package copies the document beside the output file as <output>.html before deleting the temporary one.

A snap installed Chromium cannot read /tmp of the host. Such a user sets ob-chromium-temporary-directory to a directory under $HOME that does not start with a period. The README says so (Edge cases).

Finding the executable

ob-chromium--executable returns, in order:

  1. ob-chromium-executable when it is set. When it is set and the file is not executable, user-error names the path.
  2. The first name in ob-chromium-candidates that executable-find resolves. The default list is chromium, chromium-browser, google-chrome, google-chrome-stable, chrome, chrome-headless-shell, brave-browser, microsoft-edge.
  3. The first entry in ob-chromium-candidates that is an absolute path and exists. The default list ends with the macOS application binaries of Chrome, Chromium, Brave and Edge under /Applications/*.app/Contents/MacOS/.
  4. Otherwise user-error says that no Chromium was found and names the variable.

The result is cached for the Emacs session in a variable, and the cache is cleared when the user sets ob-chromium-executable through Customize (open question 13).

The command line

The package builds a list of arguments and runs it with call-process, not through a shell (open question 2). Paths with spaces need no quoting. The list is:

Argument Source
--headless always
--disable-gpu always
--hide-scrollbars always
--user-data-dir=<profile> always (open question 8)
--window-size=<W>,<H> :width, :height, or the two defcustom defaults
--force-device-scale-factor=<N> :scale, when given (open question 14)
--default-background-color=<RRGGBBAA> :background, when given
--timeout=<ms> :timeout, else ob-chromium-timeout
--virtual-time-budget=<ms> :delay, when given
ob-chromium-extra-args each element, verbatim
:cmdline split with split-string-and-unquote, verbatim
--screenshot=<out> or --print-to-pdf=<out> or --dump-dom the mode (open question 9)
file://<document> the temporary document

:background accepts transparent, which maps to 00000000, a 6 digit hex colour, which gets FF appended, and an 8 digit hex colour, which passes through. A leading # is removed.

The output path passed to Chromium is absolute. Chromium resolves a relative path against its own working directory, and call-process runs it in default-directory, but an absolute path removes the dependency. The directory of the output file is created when it does not exist.

Running Chromium and reporting errors

ob-chromium--run calls call-process with standard output to one temporary buffer and standard error to another, and returns the exit code and both strings. Standard error is kept for the error message only. Chromium writes warnings to standard error on every run, so the package shows nothing on success (open question 11).

The execution fails when the exit code is not 0, or when the output file does not exist or is empty after Chromium exits. In both cases the package calls org-babel-eval-error-notify with the exit code and the standard error text, which opens *Org-Babel Error Output*, and then signals user-error with a one line summary. The temporary files are deleted in an unwind-protect clean-up form, so a C-g during the run leaves nothing behind.

Viewport and content fit

:fit is viewport by default (open question 6). The image is :width by :height CSS pixels, times :scale. Content below the window is not in the image.

With :fit content the package runs Chromium twice. The first run uses the same document plus one script appended before </body>: 

<script>
addEventListener("load", function () {
│ var d = document.documentElement;
│ d.setAttribute("data-ob-chromium-size",
│   │   │   │   │d.scrollWidth + "x" + d.scrollHeight);
});
</script>

The first run passes --dump-dom instead of --screenshot, with the same window size. Chromium prints the serialized DOM after the load event, so the attribute is in the output. The package reads the height from it. The second run passes --screenshot with --window-size=<W>,<measured height>. The width stays :width, because scrollWidth of the root element is never less than the window width, so a content width cannot be measured this way. When the attribute is missing from the output, the package falls back to :height and continues. Content fit costs one more Chromium start, about 1 s (Measurement).

Output file and format

The output file is :file when given, prefixed by :output-dir by org. A named block without :file gets <name>.png from :file-ext. An unnamed block without :file gets user-error with org’s own message, “did you forget to name a block?” (open question 5).

The extension picks the Chromium action (open question 9):

Extension Action
.png --screenshot=<out>
.pdf --print-to-pdf=<out> --no-pdf-header-footer
anything else user-error before Chromium starts

Chromium writes PNG from --screenshot whatever the extension says, so the package refuses other image extensions rather than write a PNG under a wrong name. For PDF, :fit is ignored and the page size comes from the document’s @page rule or Chromium’s default.

What is not covered

  • The package does not render the image inline by itself. Org does that when org-startup-with-inline-images is set or the user runs org-display-inline-images. The README gives the usual hook, (add-hook 'org-babel-after-execute-hook #'org-redisplay-inline-images).
  • The package does not install Chromium.
  • The package does not confirm evaluation. Org asks through org-confirm-babel-evaluate as for every language, and the README shows how to allow chromium blocks without a prompt.

Migration

Nothing is implemented, so nothing moves. A user of ob-html-chrome changes these:

In ob-html-chrome In ob-chromium

Edge cases

  • A browser from the same binary is already running. Chromium gets its own --user-data-dir, so it does not hand the URL to the running instance and exit (open question 8).
  • Chromium is a snap. It cannot read /tmp, so the run fails with a file not found error from Chromium. The error output names the document path. The user sets ob-chromium-temporary-directory to a directory under $HOME that does not start with a period. The README documents this (open question 7).
  • The body is a full document. It is not wrapped. <base href> and the <style> element go before </head>, or after <html> when there is no </head> (open question 4).
  • The body is empty or whitespace. user-error before Chromium starts.
  • :css names something that is neither a block nor a file. user-error names the item (open question 3).
  • :css names a block in another file. Not supported. Only the current buffer is searched. The user uses a file path instead.
  • The body references figure.png beside the org file. <base href> makes Chromium read it from there. The document itself can be in /tmp (open question 7).
  • The body loads a web font or a script from the network. Chromium has network access and the load event waits for them. --timeout bounds the wait at ob-chromium-timeout, 30 s by default. After it, Chromium captures what it has.
  • The body draws with JavaScript after a timer. :delay <ms> passes --virtual-time-budget, which runs timers ahead before capture.
  • Content is taller than :height in viewport mode. The image stops at :height. No scrollbar is drawn (open question 6).
  • Content is wider than :width in content mode. The width stays :width and the overflow is not in the image (open question 6).
  • The measurement pass gives no size attribute, because a script in the body threw before the load event or the DOM dump was cut. The package uses :height and continues. Nothing is reported.
  • Chromium exits 0 but writes no file. user-error with Chromium’s standard error in *Org-Babel Error Output* (open question 11).
  • Chromium exits non-zero. Same (open question 11).
  • The user presses C-g during the run. call-process is interrupted. The clean-up form deletes the document and the profile.
  • :file ends in .jpg or .svg. user-error before Chromium starts (open question 9).
  • :file is in a directory that does not exist. The package creates it.
  • A path contains a space. call-process takes a list, so nothing is quoted or split (open question 2).
  • Emacs runs as root in a container. Chromium refuses to start without --no-sandbox. The user adds it to ob-chromium-extra-args. The README says so.
  • :cache yes and a :css block changes. Org hashes the body and the header arguments, not the body of the named CSS block, so the cached result is stale. The user re-runs with C-u C-c C-c. The README says so (open question 3).
  • :background transparent and the body sets a body background. The image is opaque where the body paints. The template sets no background, so a fragment with no background rule is transparent.
  • Export with ox-html or ox-latex. Org executes the block during export with default-directory set to the org file’s directory, and the link to the PNG is exported as an image.
  • Windows. The file URL is built with browse-url-file-url when it exists (Emacs 29) and with file:/// and url-hexify-string otherwise. Not tested in the first version. CI runs Linux and macOS.
  • The org buffer visits a remote file over Tramp. user-error.
